# MIKASA-2 — библия данных

Источник правил — `BIBLE.orig.md` (версия пользователя). Здесь те же правила, сгруппированные по
темам; номера в скобках `(п. N)` ссылаются на пункт оригинала. Раздел 7 (чеклист загрузки на HF)
добавлен по просьбе пользователя 2026-09-22 и в оригинале не было. Раздел «Проверено на данных» —
измерения агента, не правила.

## 1. Робот и контроллер

- Робот для сбора данных и валидации в среде: **`ds_fetch`** из RoboBenchMart (robobenchmart), без
  своих модификаций (п. 8, п. 11).
- **Важно:** робот `ds_fetch` из RoboBenchMart и базовый `fetch` из ManiSkill (maniskill) имеют
  буквально разные URDF и семантику джоинтов. Делать переходы между ними **нельзя** (п. 11).
- Контроллер: **`pd_joint_pos`** (п. 12).

## 2. Действие (action), 13D (п. 13)

| Индексы | Что | Тип |
|---|---|---|
| 0-6 | 7 arm | absolute q targets |
| 7 | 1 gripper | |
| 8, 9 | 2 head (`head_pan`, `head_tilt`) | absolute targets |
| 10 | 1 torso | absolute target |
| 11, 12 | 2 base | velocities (linear / angular), не position targets |

- Движение головы **НЕ игнорируем**: 2 head absolute targets используем, то есть пишем `action[8,9]` (п. 13).
- Голова движется? **Да.** На eval не ставим `head_pan=0`, `head_tilt=0` принудительно — как и на
  сборе данных (п. 14).
- Base управляется не position targets, а linear/angular velocity (п. 13).

## 3. Проприоцепция (п. 16)

- По умолчанию `state = obs_raw["agent"]["qpos"][0]` содержит ещё и oracle-level глобальную
  информацию `(x_base, y_base, psi_base)`, которую робот вообще говоря должен сам научиться
  локализовать. Поэтому в proprioception для обучения её **не пишем**.
- `head_pan` и `head_lift` пишем, так как мы их двигаем.
- **Proprio для обучения VLA:** `proprio = obs_raw["agent"]["qpos"][0, 3:]` — 15D-3D=12D.
- **Дополнительно** в данные пишем `global_state = obs_raw["agent"]["qpos"][0, :3]` (3D) —
  глобальная информация только для дебага; на ней VLA не обучается.

## 4. Наблюдения

- 3 камеры (п. 15):

## 5. Сбор траекторий

- Пишем в **20 герц**, затем в LerobotDataset-v3 переводим в **10 герц** (п. 1).
- Собираем пока что только через motion planning, без RL (п. 6).
- Отбираем только успешные траектории (п. 2).
- SR эксперта (планировщика): стремимся в худшем случае к **>60%**. Для разных задач разный
  трешхолд; в идеале, конечно, добиваться значения повыше (п. 2).
- Рандомизация объектов и положения робота на сцене в начале эпизода — не забываем (п. 4).
- Небольшой шум к waypoints, чтобы траектории получались менее детерминированными (больше
  разнообразия -> лучше обучение VLA) — не забываем (п. 5).
- Языковые инструкции для задач должны умещаться в **100 токенов** (ориентируйтесь на токенайзер
  PaliGemma) (п. 10).
- Метаданные пишем по аналогии с
  [https://huggingface.co/datasets/mikasa-robo/mikasa-robo-vla-lerobot/blob/main/remember_color_5_long_vla_v0/source_rlds_metadata.json](https://huggingface.co/datasets/mikasa-robo/mikasa-robo-vla-lerobot/blob/main/remember_color_5_long_vla_v0/source_rlds_metadata.json):
  все сиды, длительности эпизодов, полученные награды (если есть), `success=true/false` и т. д. (п. 9).

## 6. Валидация (п. 3)

- **100 сидов**, которые не участвовали в сборе данных.
- Сид берём, только если motion planner решает задачу на `success=True`. Если не решает — берём
  другой сед (сид), и так до тех пор, пока не наберём 100 штук.
- Список сидов фиксируем для каждой задачи в отдельном `.json` файле.

## 7. Чеклист перед загрузкой датасета на HF

Каждый пункт — то, на чём споткнулся `jezv/takeitback-tray-pd-joint-pos` (2026-09-22). Проверять перед
каждой загрузкой; всё, что можно, делать в конвертере (`utils/convert_to_lerobot_stream.py`), а не руками.

**Загружаемость в LeRobot v3.0**

- [ ] В `meta/episodes/*.parquet` для каждой камеры есть все четыре колонки:
  `videos/observation.images.<cam>/chunk_index`, `.../file_index`, `.../from_timestamp`,
  `.../to_timestamp`. Когда один эпизод — один видеофайл: `from_timestamp = 0.0`,
  `to_timestamp = length / fps`. Без них LeRobot падает на первом сэмпле
  (`KeyError: 'videos/observation.images.fetch_hand/chunk_index'`).
- [ ] Проверка загрузки: `LeRobotDataset(repo_id, root=...)`, затем `ds[0]` и один сэмпл из последнего
  эпизода; оба читаются, кадры совпадают по размеру с `info.json`.

**Статистики для нормализации**

- [ ] В `meta/stats.json` для `action` и `observation.state` кроме `mean`, `std`, `min`, `max`, `count`
  есть квантили `q01`, `q10`, `q50`, `q90`, `q99`. pi0.5 (LeRobot и openpi) по умолчанию
  нормирует state и action по `q01`/`q99`; без них обучение не стартует. Считать тем же
  аккумулятором, что в `lerobot/datasets/compute_stats.py` (`DEFAULT_QUANTILES`).
- [ ] Те же квантили — в поэпизодных колонках `meta/episodes/*.parquet`
  (`stats/action/q01` и т. д.), чтобы слияние датасетов давало верные глобальные статистики.

**Соответствие правилам выше**

- [ ] `observation.state` — 12D proprio `qpos[0, 3:]`, отдельная колонка `global_state` — 3D
  `qpos[0, :3]` (п. 16). Имя колонки `global_state` без префикса `observation.`: LeRobot делает любой
  ключ `observation.*` входом политики.
- [ ] `action` — 13D в порядке таблицы раздела 2; колонки головы `action[8, 9]` не константны.
- [ ] Разрешения камер в `info.json` совпадают с таблицей раздела 4 (внешние 256x256, запястная 128x128).
- [ ] `fps` в `info.json` = 10, а траектории действительно прорежены с шагом 2
  (`utils.subsample_h5 --stride 2`), а не только перештампованы по времени (раздел 5).
- [ ] Рядом с датасетом лежит `.json` со 100 сидами валидации (раздел 6), и ни один из них не входит в
  сиды сбора (`source_seed` в `meta/episodes`).
- [ ] Метаданные эпизодов (сиды, длительности, награды, `success`) — по образцу п. 9.
