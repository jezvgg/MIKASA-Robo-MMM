# Training Physical Intelligence π0.5 on this benchmark’s LeRobot data

**Scope:** first-party-source research plus the no-fork OpenPI integration implemented in this repository. Sources include OpenPI/LeRobot source, docs, model card, and local `DATASET_CHECKLIST.md`.

## Recommendation

**Given the explicit OpenPI requirement, pin OpenPI as a submodule under `third_party/openpi`, but keep its toolchain isolated from the ManiSkill environment.** The LeRobot dataset can be loaded directly; add a small OpenPI config/transform integration for this Fetch contract. Serve inference from the OpenPI environment and call it from ManiSkill through OpenPI’s WebSocket client. Do not treat matching feature names as matching action semantics.

## Verified facts

### Two training paths

- **OpenPI:** its official fine-tuning flow uses LeRobot datasets, but requires a custom `TrainConfig`/`DataConfig` mapping from dataset keys to policy inputs, robot-specific transforms, and corresponding inference transforms. The documented flow computes normalization stats, trains with `scripts/train.py`, then serves with `scripts/serve_policy.py`. OpenPI’s LIBERO example explicitly maps images/state/actions and pads actions to model dimension, then slices model output back to task dimension. [OpenPI README](https://github.com/Physical-Intelligence/openpi/blob/main/README.md) · [OpenPI training config](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/training/config.py) · [LIBERO transforms](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/policies/libero_policy.py)
- **Native LeRobot:** `pi05` is a registered policy, trained through `lerobot-train`; its docs provide inference with `PI05Policy.from_pretrained`, standard pre/post-processors, and `select_action`. Dataset feature names can be remapped. Loading pretrained weights alone (`pretrained_path`) does not inherit all checkpoint settings; `path` loads weights plus config. [LeRobot Pi05 docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx) · [Pi05 config](https://github.com/huggingface/lerobot/blob/main/src/lerobot/policies/pi05/configuration_pi05.py) · [Pi05 model card](https://huggingface.co/lerobot/pi05_base)
- Both implementations currently expose Pi0.5’s **flow-matching action head**; OpenPI says only that head is supported for Pi0.5 training/inference. [OpenPI README](https://github.com/Physical-Intelligence/openpi/blob/main/README.md) · [LeRobot Pi05 docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx)

### Fit to this repository

- `DATASET_CHECKLIST.md` specifies `action` as 13D: 7 arm targets, gripper, 2 head targets, torso, and 2 base velocities; `observation.state` is 12D robot qpos excluding 3D base global pose. It specifies three RGB camera streams, natural-language task prompt, 10 Hz dataset cadence, and LeRobot v3.0 metadata/statistics requirements. These are **repository requirements**, not claims from upstream docs. [Local checklist](../DATASET_CHECKLIST.md)
- LeRobot Pi05 defaults pad state/actions to 32 dimensions (`max_state_dim`/`max_action_dim`); 12D state and 13D action fit mechanically. Default camera resolution is 224×224; documented Pi05 training examples use dataset image features and handle camera-key remapping/empty cameras. [Pi05 config](https://github.com/huggingface/lerobot/blob/main/src/lerobot/policies/pi05/configuration_pi05.py) · [LeRobot Pi05 docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx)
- **Recommendation:** use exactly the dataset’s 12D `observation.state`, 13D `action`, and three RGB views; map camera feature names explicitly, ensure images are RGB and correctly oriented, and preserve task text. Validate model preprocessor input and postprocessor output shapes against one real dataset episode before training.
- **Action semantics are the main integration risk.** The project action vector mixes absolute position targets with velocity commands, while state is a different-size vector. Therefore Pi05 relative-action conversion is not a safe default: its relative-action path expects a meaningful state/action correspondence. Keep relative actions disabled unless implementing and validating an explicit per-dimension transform; keep gripper/base command conventions and `env.step` timing unchanged. This is a compatibility recommendation based on local action contract and upstream transform APIs, not an upstream guarantee. [Local checklist](../DATASET_CHECKLIST.md) · [LeRobot Pi05 docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx) · [OpenPI transforms/config](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/training/config.py)
- **Memory benchmark caveat:** LeRobot exposes opt-in `use_visual_memory`; it is not implied by using a Pi05 checkpoint. With this 10 Hz dataset, set `memory_stride=10` for one-second frame spacing, and enable memory during fine-tuning, not only inference. The docs state public Pi05 checkpoints lack MEM-style memory pretraining; video history alone is a limited post-training ablation, and long-horizon language memory is not implemented. Treat this as a separate benchmark arm, not as a property of the plain Pi05 baseline. [LeRobot Pi05 memory docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx)

### Data, normalization, training, inference

- LeRobot’s Pi05 defaults to quantile normalization for state/action and identity for visual input. Pi05 docs require `q01`/`q99` in dataset stats for quantile normalization; older stats need recomputation, or select mean/std normalization explicitly. This repo checklist already requires q01/q10/q50/q90/q99. Inspect ranges and near-constant dimensions before training; bad stats can inflate normalized outputs. [Pi05 config](https://github.com/huggingface/lerobot/blob/main/src/lerobot/policies/pi05/configuration_pi05.py) · [LeRobot Pi05 docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx) · [OpenPI normalization notes](https://github.com/Physical-Intelligence/openpi/blob/main/README.md)
- LeRobot docs show full fine-tuning and a lower-memory option freezing vision/VLM portions, with gradient checkpointing and bfloat16; their LIBERO example is sized for one 80 GB GPU. OpenPI README estimates inference >8 GB, LoRA fine-tuning >22.5 GB, and full fine-tuning >70 GB on one GPU; its current training script does not support multi-node. These are upstream estimates/examples, not benchmark-specific guarantees. [LeRobot Pi05 docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx) · [OpenPI README](https://github.com/Physical-Intelligence/openpi/blob/main/README.md)
- OpenPI uses custom config/transforms for training and inference symmetry; LeRobot’s normal `preprocess` → `select_action` → `postprocess` is the simpler integration boundary. For this simulated benchmark, adapter must convert observations to LeRobot feature format and return a 13D action on the benchmark’s control cadence; chunk length/execution horizon must be measured against that cadence. [OpenPI README](https://github.com/Physical-Intelligence/openpi/blob/main/README.md) · [LeRobot Pi05 docs](https://github.com/huggingface/lerobot/blob/main/docs/source/pi05.mdx)

### OpenPI submodule integration

- OpenPI’s README explicitly uses recursive Git submodules and its own `uv` setup (`GIT_LFS_SKIP_SMUDGE=1 uv sync`, then `uv pip install -e .`). This project pins the upstream repo as `third_party/openpi`; the model dependencies stay in that environment, while only `openpi-client` is an optional root dependency. [OpenPI installation](https://github.com/Physical-Intelligence/openpi/blob/215abfb217dbac7d5f1273282331b9b1866c0479/README.md)
- **Dataset format compatibility is not automatic:** the pinned OpenPI `pyproject.toml` pins LeRobot commit `0cf864870cf29f4738d3ade893e6fd13fbd7cdb5`, whose dataset code declares `CODEBASE_VERSION = "v2.1"`. This repo's `DATASET_CHECKLIST.md` requires LeRobot v3.0. LeRobot v0.4.0 commit `f25ac02e6c8fa9c467ab8462289e5f4aed3a2e85` reads v3.0 but moved the API to `lerobot.datasets`. Setup overlays this official package in the OpenPI venv and `utils/openpi_compat.py` bridges OpenPI's old import path and task metadata shape; no OpenPI fork or submodule edit required. [Pinned OpenPI dependency](https://github.com/Physical-Intelligence/openpi/blob/215abfb217dbac7d5f1273282331b9b1866c0479/pyproject.toml) · [LeRobot v2.1 source](https://github.com/huggingface/lerobot/blob/0cf864870cf29f4738d3ade893e6fd13fbd7cdb5/lerobot/common/datasets/lerobot_dataset.py) · [LeRobot v0.4.0 source](https://github.com/huggingface/lerobot/blob/f25ac02e6c8fa9c467ab8462289e5f4aed3a2e85/src/lerobot/datasets/lerobot_dataset.py)
- Current OpenPI CLI training configs are registered in a static `_CONFIGS` list in `src/openpi/training/config.py`; it has no documented external config plugin. For a named config through the stock CLI, use a fork/patch. **No-fork option:** keep a project-owned launcher/config that constructs `TrainConfig` and calls `scripts/train.py`’s `main(config)` directly; this avoids editing the submodule but depends on an internal entrypoint, so pin OpenPI to a tested commit and keep a smoke test. [OpenPI config registry](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/training/config.py) · [OpenPI train entrypoint](https://github.com/Physical-Intelligence/openpi/blob/main/scripts/train.py)
- Pi0.5 config uses `action_dim=32` by default. Keep that model dimension for pretrained weights; pad the 12D state and 13D action to 32 in the data transform, then return only the first 13 action values from the inference output transform. OpenPI’s LIBERO transforms demonstrate this pad/slice pattern. Start with `action_horizon=10` for the 10 Hz dataset and do not apply generic delta-action conversion to the mixed position/velocity vector. [Pi0 config](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/models/pi0_config.py) · [LIBERO transforms](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/policies/libero_policy.py)
- Custom `DataConfig` should read the HF LeRobot `repo_id`, use the task string as `prompt`, map the three camera keys to OpenPI’s three image slots, resize/convert images consistently, and map `observation.state` unchanged before padding. Compute normalization stats with OpenPI’s script using this config.
- For eval, keep the benchmark process in its ManiSkill environment and call OpenPI through `WebsocketClientPolicy`. The stock `scripts/serve_policy.py` also resolves a registered config name, so a no-fork setup needs a small project-owned server launcher: call `policy_config.create_trained_policy(custom_train_config, checkpoint)` and pass it to `WebsocketPolicyServer`. OpenPI documents remote serving specifically to avoid dependency conflicts. Consume the returned action chunk at dataset cadence, holding each 10 Hz action for two 20 Hz simulator steps. [OpenPI remote inference](https://github.com/Physical-Intelligence/openpi/blob/main/docs/remote_inference.md) · [Policy loader](https://github.com/Physical-Intelligence/openpi/blob/main/src/openpi/policies/policy_config.py)

## Suggested first run

1. Initialize the upstream OpenPI submodule recursively; set up its isolated `uv` environment and overlay the pinned LeRobot v3 loader.
2. Run the adapter self-check and `utils.openpi_train --mode check` against the actual HF repo. This validates v3 loading, task prompts, three RGB views, 12D state, and 13D actions.
3. Compute stats, train, serve the checkpoint, and run one ManiSkill episode through the WebSocket evaluator.
4. Evaluate held-out seeds with the same physics backend. A successful pipeline proves data/action integration, not persistent memory capability of standard Pi0.5.

**Recommendation boundary:** upstream docs establish supported APIs and defaults. They do not establish Pi0.5 performance on this Fetch simulator, viability of the mixed 13D action contract, or success with these cameras/data. Those require experiment.
