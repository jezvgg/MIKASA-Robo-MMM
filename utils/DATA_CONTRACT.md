# Контракт данных MIKASA

Общая спецификация записи, экспорта и оценки задач. Под `ds_fetch` понимается
робот из `master` репозитория `jezvgg/MIKASA-Robo-MMM`. Для текущего профиля
закреплён commit `4c5c8b3de941565ee2d57b153a10254fe64c2849`; файлы модели
робота сохраняются без изменений. Версия, настройки и результаты проверки
конкретного выпуска сохраняются отдельно от нормативных требований.

## Требования

1. Записывать траектории при частоте управления **20 Гц**, затем переводить
   в **LeRobotDataset v3 при 10 Гц**. Частота физики — отдельная величина.
   Изменение fps в метаданных само по себе не преобразует траекторию.
2. Стремиться к SR motion-planning эксперта **>60%**; ориентиры задавать по
   задачам и по возможности повышать. В обучающий набор включать **только
   успешные траектории**. SR считать по исходным попыткам, до фильтрации.
3. Для каждой задачи отобрать **100 уникальных validation seeds**, которые
   не участвовали в сборе обучающих данных. Принимать seed только после
   фактического **success=True** motion planner в среде. Неуспешный кандидат
   заменяется следующим до набора 100. Для каждой задачи фиксировать отдельный
   JSON. После фиксации не заменять seeds по результатам оцениваемой VLA.
4. Рандомизировать объекты и начальное положение робота. Сохранять seed и
   параметры рандомизации для воспроизведения начальной сцены.
5. Добавлять небольшой шум к waypoints для разнообразия траекторий. Сохранять
   seed шума, амплитуды и распределение; проверять допустимость движения после
   возмущения. Случайность RRT сама по себе не выполняет этот пункт.
6. Пока собирать демонстрации **только motion planning, без RL**.
7. Записывать изображения **только RGB, без depth**.
8. Использовать **`ds_fetch` из ветки `master` репозитория
   `jezvgg/MIKASA-Robo-MMM` без наших изменений в файлах робота**.
   Текущий закреплённый commit: `4c5c8b3de941565ee2d57b153a10254fe64c2849`.
   Сохранять исходные класс, контроллеры, камеры, URDF/SRDF и meshes этой версии.
   Исторический RoboBenchMart не подставлять вместо робота из `master`.
   Для каждого выпуска фиксировать точный commit: движение ветки `master`
   само по себе не обновляет робота в уже записанных данных.
9. Записывать исходные метаданные по аналогии с
   [source_rlds_metadata.json](https://huggingface.co/datasets/mikasa-robo/mikasa-robo-vla-lerobot/blob/main/remember_color_5_long_vla_v0/source_rlds_metadata.json):
   все seeds, длины и длительности эпизодов, доступные rewards, success/failure
   и происхождение данных. Неуспешные попытки сохраняются в журнале сбора,
   хотя их траектории не включаются в обучающий набор.
10. Языковая инструкция должна занимать **не более 100 токенов PaliGemma**.
    Проверять полный текст до записи, без молчаливого обрезания. Зафиксировать
    версию/хеш токенайзера и способ учёта специальных токенов.
11. Для **сбора, повторного исполнения, RGB и валидации использовать одну
    и ту же закреплённую версию `ds_fetch` из `master`**, выбранную в пункте 8.
    Базовый fetch из ManiSkill имеет другой URDF и семантику суставов:
    подмена запрещена. Переименование articulation в сохранённом состоянии
    не делает этих роботов взаимозаменяемыми.
12. Контроллер на всех этапах — **pd_joint_pos**.
13. **Action 13D**: 7 абсолютных целей руки, 1 команда gripper, 2 абсолютных
    цели головы, 1 абсолютная цель torso, 2 команды скорости базы. Каналы
    головы **8 и 9** сохраняются и исполняются. База получает linear/angular
    velocity, а не position targets.
14. Голова движется и при сборе, и на eval. Не обнулять принудительно
    head_pan/head_tilt; не заменять каналы головы константами в адаптерах.
15. RGB observations — **ровно три камеры**: left external **256×256, FOV 1.5**;
    wrist **128×128, FOV 2.0**; right external **256×256, FOV 1.5**.
    FOV указан в радианах. Фиксированная камера сцены не входит в наблюдения VLA.
    Не уменьшать все камеры до 128×128 при хранении.
16. Обучение и inference получают **proprio 12D**:
    proprio = obs_raw["agent"]["qpos"][0, 3:].
    Отдельно записывать **global_state 3D**:
    global_state = obs_raw["agent"]["qpos"][0, :3] = (x_base, y_base, psi_base).
    Это поле только для диагностики: VLA на нём не обучается и его не получает.
    Суставы головы и torso остаются в proprio.

В исходном пункте 16 написано head_lift; в пункте 14 и текущем коде наклон
головы называется head_tilt, а подъём корпуса — torso_lift. Операционное
требование пункта 16 — точный срез qpos[3:], без исключения этих суставов.
Порядок qpos нельзя выводить из порядка action.

## Раскладка action

Индексы нулевые, срезы используют правила Python.

| Индекс/срез | Размер | Смысл |
|---|---:|---|
| action[0:7] | 7 | Абсолютные положения суставов руки |
| action[7] | 1 | Gripper в штатной семантике контроллера DSFetch |
| action[8:10] | 2 | Абсолютные head_pan, head_tilt |
| action[10] | 1 | Абсолютный torso_lift |
| action[11:13] | 2 | Скорость движения вперёд и скорость поворота |

Нормализацию и масштаб gripper/base брать из закреплённого штатного
контроллера и записывать явно. Нормализованная команда скорости не равна
физической скорости без применения соответствующего масштаба.

Проверять имена и порядок активных суставов перед срезом qpos. Если размерность
или порядок другой, прекращать экспорт, а не молча обрезать массив.
Полные qpos 15D могут оставаться в исходном H5 для replay/диагностики.
Обучаемое observation.state содержит только 12D proprio; global_state
не включается в policy input, токенизацию state и обучающую нормализацию.

## Запись и метаданные

Сначала записываются состояния и команды H5 при 20 Гц. В H5 на T действий хранится
T+1 состояний. Исходные действия повторяются в новой среде; для 10 Гц первая цель
каждой пары удерживается два шага по 0.05 с. Нечётный конец дополняется удержанием.
Успех преобразованной траектории проверяется заново. RGB строится из проверенных
состояний; восстановление состояния для изображения не является физическим повтором.
В train проходят только успешные записи. Неудачные попытки остаются в журнале.

Метаданные сохраняют задачу, вариант, seeds сцены/планировщика/шума, инструкции,
длины и длительности, частоты, reward_sum, результаты этапов, версии робота,
движка и исходников, камеры, имена суставов, единицы команд и правила отбора.
`success` — успех на последнем записанном шаге, `success_once` — хотя бы на одном
шаге полной истории 20 Гц. Оба вычисляются из H5 и проверяются при экспорте;
успех хотя бы раз не заменяет финальный успех. Для ошибки без полной записи
результат явно неизвестен (`null`), а не подменяется успешным/неуспешным эпизодом.

Экспорт создаёт настоящий LeRobotDataset v3 и `source_h5_metadata.json` с
соответствием эпизодов исходным H5 и со всеми попытками сбора. Проверка чтения
сравнивает команды, положения суставов, время, сводные метаданные и выборку RGB.
`policy_inputs` содержит только proprio 12D, три RGB и текст; `global_state 3D`
остаётся отдельным полем для диагностики. Будущий trainer должен соблюдать
этот список входов.

## Независимая проверка

Выбор 100 validation seeds определяется исходным motion planner при 20 Гц.
Результат повторного исполнения 10 Гц записывается отдельно и не меняет этот отбор.
Исключаются все сиды обучающих попыток и разработки, включая неудачные.
Проверочный JSON содержит список, происхождение и результаты кандидатов.
Нельзя заменять сид после неудачи оцениваемой модели.

Описание конкретной задачи и команды запуска: [CabinetSearch](collection/CABINET_SEARCH.md).
