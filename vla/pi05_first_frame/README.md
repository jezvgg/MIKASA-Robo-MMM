# pi0.5 + первый кадр эпизода: бейзлайн OpenSameDrawer

OpenSameDrawer — задача на память. В начале эпизода один из четырёх ящиков колонны открыт: это подсказка. Робот закрывает его, и после этого все ящики выглядят одинаково. Затем он переносит яблоко на тарелку у дальней стойки (~40 с) и должен вернуться и открыть **тот же** ящик.

Обычный pi0.5 видит только текущий шаг, поэтому верный ящик он угадает примерно в четверти случаев. В этом бейзлайне модель получает **четвёртое изображение** — кадр 0 эпизода с левой головной камеры, где подсказка видна. Оно подаётся и при обучении, и при проверке в среде. Первые три изображения — текущие кадры левой и правой головных камер и камеры в руке.

Цель — SR > 80% на 100 закреплённых валидационных сидах (`validation_seeds.json` набора, H4).

- Модель: pi0.5 из openpi (JAX), полный fine-tune от `pi05_base`.
- Данные: [`nurtayev-d/samedrawer-1000ep`](https://huggingface.co/datasets/nurtayev-d/samedrawer-1000ep), ревизия `d126eba`. Это LeRobot v3.0: 1000 эпизодов, 560 900 кадров, 10 Гц.

## Как устроено

| Файл | Что делает |
|---|---|
| `OPENPI_COMMIT`, `openpi.patch` | openpi `215abfb` + правка на 17 строк: (а) `Pi0Config.image_keys` — список изображений настраивается; (б) `DataConfig.dataset_factory` — своё чтение данных вместо LeRobot 0.1.0, который не читает v3.0 |
| `src/mikasa_pi05/dataset.py` | читает v3.0 напрямую: числа из parquet, кадры из mp4 через PyAV; к каждому примеру добавляет кадр 0 того же эпизода. Сверено с LeRobot 0.4.3: 144 кадра совпали бит в бит |
| `src/mikasa_pi05/transforms.py` | раскладка камер по слотам модели, перестановка state в порядок действий, маска дельт |
| `src/mikasa_pi05/configs.py` | конфиги `pi05_sd_ff_dummy`, `pi05_sd_ff_overfit`, `pi05_sd_ff_1xh100`, `pi05_sd_ff_4xh100` |
| `src/mikasa_pi05/cli.py` | `python -m mikasa_pi05 norm-stats / train / serve`; train и serve — это собственные скрипты openpi |
| `eval_samedrawer.py` | проверка в среде (venv симулятора): первый кадр запоминается после `reset` и прикладывается к каждому запросу; цикл `run_policy_episode` из `utils/collection/client.py` |
| `scripts/setup_server.sh` | установка на чистый сервер без root |
| `scripts/check_server.sh` | проверки после установки (~5 мин) |
| `scripts/eval_parallel.sh` | оценка на нескольких GPU: сервер политики и шард сидов на каждой |
| `scripts/fix_vulkan.sh` | ищет файл драйвера Vulkan, с которым рендер идёт на NVIDIA |
| `requirements-sim.txt`, `overrides-sim.txt` | окружение симулятора = окружение, в котором записан набор |
| `tests/` | pytest для стороны openpi; сверка с LeRobot; рендер против набора; инференс на `pi05_base` |

Ключевые решения:

- **Слоты изображений:** `base_0_rgb` ← левая головная, `left_wrist_0_rgb` ← камера в руке, `right_wrist_0_rgb` ← правая головная, `base_1_rgb` ← кадр 0 левой головной. Слоты без «wrist» в имени получают при обучении случайный кроп и поворот, причём `base_0` и `base_1` одинаковые.
- **Подсказку видно на кадре 0.** Простой классификатор по пикселям угадывает ящик на отложенных эпизодах в 92% случаев по левой камере и в 94% по правой; случайное угадывание — 31%.
- **Состояние** (12 чисел `qpos[3:]`) идёт текстом в промпт (`discrete_state_input=True`); вместе с инструкцией это меньше 200 токенов.
- **Действия.** Для суставов руки, головы и торса модель учит отклонение от текущего положения; на выходе оно снова превращается в абсолютную цель. Схват и скорости базы остаются абсолютными. Горизонт — 10 шагов (1 с). В среде повторное планирование идёт каждые 5 шагов, каждое действие держится 2 тика по 20 Гц, как при записи.
- **Ветка начинается от `feat/same-drawer-collection` (`c64a4fd`).** Её отпечаток кода `a39d1c42…` совпадает с тем, под которым записаны набор и валидационные сиды. `eval_samedrawer.py` сверяет отпечатки кода и движка и при расхождении не запускается. Новый код лежит в `vla/`, которая в отпечаток не входит.
- **Движок — `mani_skill==3.0.0b22` с PyPI**, а не форк `../ManiSkill` из `pyproject.toml`: данные записаны на нём (отпечаток `74ecf1d0…`).

## Установка на сервере (без root)

```bash
git clone -b feat/pi05-first-frame-samedrawer https://github.com/pa40l/MIKASA-Robo-MMM.git ~/mikasa-pi05/MIKASA-Robo-MMM
~/mikasa-pi05/MIKASA-Robo-MMM/vla/pi05_first_frame/scripts/setup_server.sh      # ~45 ГБ, повторный запуск безопасен
. ~/mikasa-pi05/server.env                                                        # перед каждой командой
$REPO_DIR/vla/pi05_first_frame/scripts/check_server.sh --base                     # все проверки, включая pi05_base
```

Что поставит скрипт:
- uv (если его нет);
- openpi с правкой и его venv (~12 ГБ);
- venv симулятора (~7 ГБ);
- сцены RoboCasa (~8 ГБ);
- набор (~14 ГБ);
- веса pi05_base (~12 ГБ).

Пути можно переопределить через переменные, например `PI05_WORK=/data/me/pi05`.

**Не используйте переменные с префиксом `MIKASA_`:** профиль симулятора их запрещает.

Если драйвер старше 580, torch для симулятора ставится в сборке под CUDA 12.6 (`2.14.0+cu126`). Обычная сборка с PyPI требует CUDA 13, а рендер передаёт картинки камер в torch прямо на GPU.

## Дебаг на 1×H100

```bash
. ~/mikasa-pi05/server.env; cd $REPO_DIR; PY=$OPENPI_DIR/.venv/bin/python
export CUDA_VISIBLE_DEVICES=0                 # свободная карта из check_server.sh
$PY -m mikasa_pi05 norm-stats pi05_sd_ff_4xh100   # одна статистика на все конфиги, ~1 мин

# 1. Переобучение на 10 эпизодах: модель должна решить сиды этих эпизодов.
nohup $PY -m mikasa_pi05 train pi05_sd_ff_overfit --exp-name overfit1 > $PI05_WORK/logs/overfit1.log 2>&1 &
vla/pi05_first_frame/scripts/eval_parallel.sh pi05_sd_ff_overfit \
    $PI05_WORK/checkpoints/pi05_sd_ff_overfit/overfit1/1999 $PI05_WORK/results/overfit1 0 --seeds train:10 --video 3

# 2. Короткий прогон на всём наборе: время шага, память, первые 20 валидационных сидов.
nohup $PY -m mikasa_pi05 train pi05_sd_ff_1xh100 --exp-name debug1 > $PI05_WORK/logs/debug1.log 2>&1 &
vla/pi05_first_frame/scripts/eval_parallel.sh pi05_sd_ff_1xh100 \
    $PI05_WORK/checkpoints/pi05_sd_ff_1xh100/debug1/2999 $PI05_WORK/results/debug1 0 --max-episodes 20 --video 5
```

Если полный fine-tune не влезает в одну H100, уменьшите батч: `--batch-size 16`. Любое поле конфига переопределяется так же: `--num-train-steps`, `--lr-schedule.peak-lr` и т. д. wandb включается сам, если задан `WANDB_API_KEY`.

## Обучение на 4×H100 и оценка

```bash
CUDA_VISIBLE_DEVICES=0,1,2,3 nohup $PY -m mikasa_pi05 train pi05_sd_ff_4xh100 --exp-name run1 \
    > $PI05_WORK/logs/run1.log 2>&1 &            # 30k шагов, batch 128, FSDP на 4 карты; продолжить: --resume
vla/pi05_first_frame/scripts/eval_parallel.sh pi05_sd_ff_4xh100 \
    $PI05_WORK/checkpoints/pi05_sd_ff_4xh100/run1/29999 $PI05_WORK/results/run1-29999 0,1,2,3 --video 10
# контроль: та же модель с чёрным кадром вместо подсказки — верный ящик должен угадываться ~1/4
vla/pi05_first_frame/scripts/eval_parallel.sh pi05_sd_ff_4xh100 \
    $PI05_WORK/checkpoints/pi05_sd_ff_4xh100/run1/29999 $PI05_WORK/results/run1-29999-black 0,1,2,3 --first-frame black
```

Итог пишется в `summary.json`:
- SR с 95% доверительным интервалом;
- SR по ящикам;
- этапы: закрыл подсказку / положил яблоко / открыл верный ящик / открыл чужой;
- статусы эпизодов.

По каждому сиду есть строка в `shard-*/episodes.jsonl`, видео лежат в `shard-*/videos/`.

Сиды валидации не менять после оценки модели (DATA_CONTRACT).

Этап «закрыл подсказку» может засчитаться и случайно: робот задевает ящик рукой. Смотрите на всю цепочку этапов.

## Что проверено здесь (RTX 2000 Ada 16 ГБ, 2026-10-04)

- Чтение данных = LeRobot 0.4.3 (144 кадра, разница 0). Кадр 0, повтор последнего действия в конце эпизода и преобразования туда-обратно проверены (pytest, 5 тестов). Промпт со state меньше 200 токенов.
- **Dummy-обучение** (`pi05_sd_ff_dummy`, маленький Gemma): 50 шагов на реальных данных с 4 изображениями, loss конечный, чекпойнт сохранён. Сервер с этим чекпойнтом + `eval_samedrawer.py`: метаданные совпали, первый кадр уходит в каждом запросе, действия исполняются.
- **pi05_base + 4 изображения:** веса грузятся, инференс 0,36 с, 6,5 ГБ памяти.
- **Записанные действия 2 обучающих эпизодов** через тот же цикл оценки: 2/2 успеха.
- **Живой рендер против кадров набора:** в среднем 1,1–1,5 из 255 (соседний кадр 2–9, другой эпизод 16–27).
